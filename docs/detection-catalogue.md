# Detection catalogue

Every DwellWatch rule: what it catches, what else it could catch, its ATT&CK technique, and what
each SIEM gets from it. The Sigma rules in [`sigma/`](../sigma) are the source of truth. Everything
in [`converted/`](../converted) is generated from them by `python -m dwellwatch.convert` (or
`make convert`); CI fails if a rule changes and the conversions are not regenerated.

## Conversion targets

| Target | Files | Event sources it covers | How it is produced | How it is checked |
|---|---|---|---|---|
| **Wazuh 4.14.8** | `converted/wazuh/*.xml`, local rules | Sysmon event 1, Security 4688, and successful Security audit events for `service: security` rules | Generated by `dwellwatch.convert`; Wazuh has no pySigma backend | Every pattern compiled with PCRE2, the engine behind Wazuh's `type="pcre2"`. On planted events and the pinned datasets (in CI), and once on the 392,824 events of the [unseen-data round](lab-architecture.md#tested-on-data-the-rules-were-not-written-against) (30 alerts each with the stage 1 rules included, no disagreement), the Wazuh rules fire on exactly the events the replay engine flags, using a model of how Wazuh decodes Windows events ([`tests/wazuh_model.py`](../tests/wazuh_model.py)). Not yet loaded into a running Wazuh manager; that is part of the live lab |
| **Splunk** | `converted/splunk/*.spl` | Sysmon event 1 (fields `Image`, `CommandLine`, `OriginalFileName`, as the Splunk Add-on for Sysmon extracts them); Security events by their EventData names (`TargetUserName`, `TargetSid`), as the Splunk Add-on for Windows extracts them with `renderXml = true` | pySigma Splunk backend | The shape of the query is asserted; not run against Splunk |
| **Microsoft Sentinel** | `converted/sentinel/*.kql` | Process creation: ASIM `imProcessCreate`, which normalises Sysmon event 1, Security 4688 and Defender for Endpoint process events. Security-log rules: the `SecurityEvent` table, where the Windows Security Events connector puts them | pySigma Kusto backend with its `sentinel_asim` pipeline, or for Security-log rules its Azure Monitor pipeline, plus two DwellWatch fixes (below) | The shape of the query is asserted; not run against Sentinel |

Prepend your own scope to the Splunk searches (for example
`index=windows sourcetype="XmlWinEventLog:Microsoft-Windows-Sysmon/Operational"` for the
process rules, `index=windows source="XmlWinEventLog:Security"` for the Security-log rules); the
rules match on fields only. Splunk evaluates `OR` before `AND`, so in
`EventID IN (4728, 4732, 4756) TargetSid IN (...) OR TargetUserName IN (...)` both group
alternatives sit under the EventID filter, as the Sigma rule says.

## What does not convert, and why

The converter never writes a query it knows to be wrong. When a target cannot express a rule, it
raises `UnsupportedForTarget` with the reason, and the rule is listed as not converted.

**KQL.** Process-creation rules convert to Sentinel's ASIM tables. They would **not** convert to
Sentinel's `SecurityEvent` table (pySigma's Azure Monitor pipeline): every stage 5 rule matches a
renamed binary by `OriginalFileName`, which Sysmon records and Security 4688 does not. Rather than
drop that half of each rule, Sentinel output targets ASIM, whose parsers bring Sysmon's field in.
Security-log rules (`service: security`) go the other way: pySigma's ASIM pipeline maps log
categories (process, file, registry, network, web) and has no table for them, while
`SecurityEvent` carries each event's EventData fields as columns.
A Sysmon event type with no ASIM table at all, such as named pipes (Sysmon 17 and 18), is refused
for Sentinel; `tests/test_convert.py` pins that.

**Splunk.** The SPL covers Sysmon's field names only. Security 4688 reaches Splunk under
different names (`New_Process_Name`, `Process_Command_Line` in the Windows add-on), so 4688
coverage in Splunk needs a field mapping that is not written yet.

**Wazuh.** Negated conditions (`not filter`), keyword searches, and a regex that has to match a
literal backslash are refused for now. No current rule uses them.

### Upstream problems found and worked around

- **pySigma's Splunk backend and a regex inside an OR.** It emits a `rex`/`eval` chain that either
  starts with no base search or leaves part of the OR stranded in a trailing `| search OR ...`.
  Neither runs as written. The converter refuses such output, and the two rules that had it
  (bcdedit, PowerShell) were rewritten: bcdedit folds its two alternatives into one regex, and the
  PowerShell rule matches the `rwmi` and `rcim` aliases with `contains`. A single regex ANDed with
  the rest becomes a clean `| regex` filter.
- **pySigma-backend-kusto 1.0.1's ASIM pipeline** maps `OriginalFileName` to two fields, one of
  which (`TargetProcessFilename`) is not in its own `imProcessCreate` schema, so every rule using
  it fails to convert. DwellWatch maps `OriginalFileName` to `TargetProcessFileOriginalName` first.
- **pySigma-backend-kusto 1.0.1 quotes the numbers in a list** and compares them with `in~`, the
  case-insensitive string operator: `EventID in~ ("4728", "4732", "4756")`. `SecurityEvent`'s
  `EventID` is an integer column. DwellWatch writes such a list as numbers,
  `EventID in (4728, 4732, 4756)`, so the query does not depend on Kusto converting between types.
- **pySigma processing pipelines rewrite the parsed rule in place**, so a rule parsed once and
  converted for two targets carries the first target's field names into the second. The converter
  parses the rule afresh for every target.

## Wazuh specifics

These were checked against Wazuh 4.14.8's own ruleset and analysisd source, not assumed:

- **Parents.** Sysmon event 1 rules use `<if_group>sysmon_event1</if_group>`, the group rule 61603
  sets, as Wazuh's own Sysmon rules do. Security rules, 4688 included, hang from rule **60103**
  (successful audit events), where Wazuh's own rules for successful Security events hang, and
  match `win.system.eventID`. A rule on an audit failure, such as a failed logon (4625), would
  need 60104 instead; none exists yet.
- **Field names.** Wazuh names Windows EventData fields in lowerCamelCase under `win.eventdata`
  (`Image` is `win.eventdata.image`; 4688's `NewProcessName` is `win.eventdata.newProcessName`;
  `TargetUserName` is `win.eventdata.targetUserName`). The event ID is `win.system.eventID`.
- **Escaping.** Wazuh keeps Windows event values JSON-escaped: a path such as
  `C:\Windows\System32\vssadmin.exe` arrives as `C:\\Windows\\System32\\vssadmin.exe`, and a quote
  arrives as `\"` (see the events in Wazuh's `ruleset/testing/tests/sysmon_eid_1.ini`). A pattern
  written for the raw value would fail on paths. The generator makes every backslash in a Sigma
  value match one or two backslashes, and every quote an optional backslash first, so the rules
  hold either way.
- **Levels.** Wazuh orders sibling rules by level, highest first, puts built-in rules before local
  ones on a tie, and stops at the first match (`_OS_AddRule` in `src/analysisd/rules_list.c`), so
  a DwellWatch rule must outrank every built-in sibling that could match the same event. Sigma
  `medium` becomes Wazuh level **10** and `high` **13**.
  - *Security events.* Under 60103, Wazuh's own rules go up to level 9 (60115, account locked
    out), so a DwellWatch rule at 10 or 13 is always tried first. Wazuh's own group-change rule
    (60113, level 5, with the member-added rules 60141, 60144 and 60151 beneath it) and its
    account-change rule (60110, level 8) fire only when no DwellWatch rule matches. Wazuh has no
    rule for a password reset (4724).
  - *Sysmon event 1.* At 12, a DwellWatch rule would lose an encoded-PowerShell deletion started
    from PowerShell, REvil's technique, to Wazuh's rule 92057 (PowerShell spawning PowerShell with
    an encoded command, level 12). At 13 it outranks every level-12 Sysmon rule. Of the built-in
    Sysmon process rules at 13 and above (certutil, Defender side-loading, `.js` execution,
    right-to-left file names, rundll32), only 92062 (level 14) can match one of these commands: it
    fires when `control.exe` starts PowerShell at high integrity, a UAC bypass. A shadow-copy
    deletion run in exactly that chain would be reported as 92062 instead of the DwellWatch rule.
- **IDs.** Each Sigma rule owns a block of ten IDs in the local range, recorded in
  [`sigma/wazuh-ids.yml`](../sigma/wazuh-ids.yml), so numbers stay stable as rules are added.
  One Sigma rule becomes several Wazuh rules, because a Wazuh rule's conditions can only be ANDed:
  each branch of the Sigma condition (binary by path, or by original file name) becomes its own
  rule, for each event source that has the fields. Alternatives that test the same field stay in
  one rule: the group rule's SID suffixes and whole SIDs are one pattern, its group names another.

To try them on a Wazuh manager, copy `converted/wazuh/*.xml` into `/var/ossec/etc/rules/`,
restart the manager, and paste an event into `/var/ossec/bin/wazuh-logtest`.

## Stage 1: help-desk reset abuse

Both rules read the Windows Security log (Sigma `service: security`): the domain controllers' for
domain accounts and groups, each host's for its local groups. Real-data results are in
[lab-architecture.md](lab-architecture.md#stage-1-on-real-data).

| Rule | ATT&CK | Level | Catches | Stays quiet on | False positives | Known gaps |
|---|---|---|---|---|---|---|
| [Password Reset On Another Account](../sigma/stage1_helpdesk/password_reset_by_another_account.yml) | T1098 (and T1078) | medium | 4724: one account resetting another's password. The signal names the reset account, the one the caller now holds | 4723 (users changing their own password), 4738, account creation and enabling | Every reset the service desk does. Alone it should feed correlation, not page anyone | An MFA reset, and a reset done in a cloud identity provider and not written back to AD (below) |
| [Member Added To A Privileged Group](../sigma/stage1_helpdesk/privileged_group_member_added.yml) | T1098 | high | 4728, 4732, 4756 into Domain, Enterprise, Schema, Key or Enterprise Key Admins, Administrators, Account, Server or Backup Operators, or DnsAdmins; matched by well-known SID and by name. The signal names the account that made the change | Other groups (Users, Remote Desktop Users, a workstation's `None`), a member removed (4729), the group itself changed (4737), a RID that merely ends in 512 | Planned administrator changes, which should be rare and go through change control | A group nested inside a privileged group: the event names the group changed, not the one it grants. Powerful groups not listed (Group Policy Creator Owners, Print Operators, groups given admin rights by delegation) |

Decisions behind these two rules:

- **No rule for 4738** ("user account changed"). Windows logs one with every reset: the bulk
  reset run has 40 resets and 40 of these. A 4738 rule would count each reset twice.
- **MFA resets (T1556) are not in Windows logs.** MFA methods live in the identity provider
  (Entra ID, Okta), so resetting them leaves nothing for these rules. Catching it needs that
  provider's audit log, which this lab does not collect. The same goes for a password reset done
  in the cloud and not written back to Active Directory.
- **The reset rule is medium on purpose.** A reset is what a service desk does all day; the
  attack is a reset followed by discovery, credential theft or backup deletion on the same
  account, which is what correlation (Phase 4) looks for. The group rule is high because adds to
  these groups should be rare.

Each rule has must-fire and must-stay-quiet tests in
[`tests/test_replay_stage1.py`](../tests/test_replay_stage1.py).

## Stage 5: backup destruction

All six rules: ATT&CK **T1490** (Inhibit System Recovery), Sigma level `high`, log source
`process_creation` (Sysmon 1, Security 4688). Each matches the binary by path and by
`OriginalFileName`, so a renamed copy is still caught, and each alerts on the process that does
the damage, not on the shell that launched it. Real-data results are in
[lab-architecture.md](lab-architecture.md#tested-on-data-the-rules-were-not-written-against).

| Rule | Catches | Stays quiet on | False positives | Known gaps |
|---|---|---|---|---|
| [Shadow Copies Deleted With vssadmin](../sigma/stage5_backup_destruction/vssadmin_shadow_delete.yml) | `vssadmin delete shadows`, any case and arguments | `vssadmin list shadows`, `create shadow`, `list shadowstorage` | Backup software or an administrator pruning old copies (`/oldest`) | `vssadmin resize shadowstorage /maxsize=401MB`, which Clop uses to make Windows discard copies |
| [Backup Catalogue Deleted With wbadmin](../sigma/stage5_backup_destruction/wbadmin_delete_catalog.yml) | `wbadmin delete catalog` | `wbadmin start backup`, `get versions`, `delete systemstatebackup -keepVersions:3` | Rebuilding a corrupted catalogue, a documented recovery step | `wbadmin delete systemstatebackup -keepVersions:0` (deletes every system-state backup) |
| [Windows Recovery Disabled With bcdedit](../sigma/stage5_backup_destruction/bcdedit_recovery_disabled.yml) | `recoveryenabled` set to no, off, false or 0; `bootstatuspolicy ignoreallfailures` | `recoveryenabled yes`, `bootstatuspolicy displayallfailures`, `bcdedit /enum` | Kiosk or lab images that suppress the recovery screen at build time | `reagentc /disable`, which turns off the recovery environment another way |
| [Shadow Copies Deleted With wmic](../sigma/stage5_backup_destruction/wmic_shadowcopy_delete.yml) | `wmic shadowcopy delete`, `where ... delete`, `path win32_shadowcopy delete` | `wmic shadowcopy list`, `call create`, `wmic process ... delete` | Clean-up scripts that use wmic instead of vssadmin | wmic on a remote host (`/node:`) alerts on the machine running wmic, not the one losing its copies |
| [Shadow Copies Deleted With PowerShell](../sigma/stage5_backup_destruction/powershell_shadowcopy_delete.yml) | `Win32_ShadowCopy` with `.Delete()`, `Remove-WmiObject`, `Remove-CimInstance`, `rwmi` or `rcim` | Listing copies, creating them with `.Create()` | An administrator clearing old copies from PowerShell | A class name built from pieces; script files run with `-File` (their content is not on the command line) |
| [Shadow Copies Deleted With Encoded PowerShell](../sigma/stage5_backup_destruction/powershell_encoded_shadowcopy_delete.yml) | The same, hidden with `-EncodedCommand` (base64 of UTF-16), as REvil does | Other encoded commands, including Atomic Red Team's own runner | Management tooling that deletes copies through encoded PowerShell; encoding is rare in real administration | Other spellings (`WIN32_SHADOWCOPY`), because matching is on the encoded bytes; PowerShell script block logging (4104) would close this |

Each rule has must-fire and must-stay-quiet tests in
[`tests/test_replay_stage5.py`](../tests/test_replay_stage5.py), and loosening any rule to its
naive form (dropping the destructive verb) fails them.
